= Release Process

== Ownership

Only a maintainer publishes artifacts, creates tags, or marks a GitHub release final. A merged release-preparation pull request does not authorize deployment or publication.

== Shared standard

This lifecycle is the standard for AssertJ QuickFIX/J, FixMock, and the QuickFIX/J Spring Boot starter:

* Prepare the release on a `release/<version>` branch from a green mainline.
* Commit the exact non-SNAPSHOT version, changelog, SCM tag, and documentation before deployment.
* Keep the Central publishing plugin, source JAR, Javadoc JAR, signing, and release-only Enforcer rules in the `release` Maven profile.
* Configure Central with `autoPublish=false` and `waitUntil=validated`.
* Upload and validate first. Publish separately in the Central Portal after inspection.
* Create the Git tag only after Central reports the deployment as `PUBLISHED`.
* Prepare the next development SNAPSHOT in a separate pull request.

Preserve the historical `v0.1.0` tag. Use plain semantic versions for new tags, beginning with `0.2.0`.

== Version preparation

Create `release/<version>` from a green `main` branch. Update the parent and all reactor modules together:

[source,shell]
----
mvn --batch-mode versions:set \
  -DnewVersion=<version> \
  -DgenerateBackupPoms=false
----

Update the external `consumer-pom.xml` fixture to consume the same release version. Confirm the published POM SCM tag, README examples, changelog, and compatibility documentation use the intended version.

For each release, confirm:

* The parent and all five reactor modules use the intended release version.
* `consumer-pom.xml` consumes the intended release version.
* The published POM SCM tag is the intended release version.
* README installation examples use the intended release version.
* The changelog contains a dated section for the intended release version.

== Verification

Run the canonical build and release artifact build from a clean checkout:

[source,shell]
----
mvn --batch-mode clean verify
mvn --batch-mode clean verify -Dquickfixj.version=3.0.2
mvn --batch-mode -Prelease -Dgpg.skip=true clean verify
----

Record Java 17 and 25 results with QuickFIX/J 2.3.2 and 3.0.2; peer-side transport results in both roles; JUnit, REST, lifecycle, example, and integration results; packaged-consumer results; dependency convergence; 80 percent core line coverage; japicmp compatibility with the previous public release; source and Javadoc archives; and required ecosystem interoperability results. Record explicit deferrals for fixtures assigned to later milestones.

The release profile rejects SNAPSHOT project versions and SNAPSHOT dependencies. Normal verification must not resolve the release-only Central publishing extension.

== Credentials and signing

Configure a Central Portal user token under server ID `central` in the maintainer's Maven `settings.xml`. Do not commit credentials.

Use GPG key `E669C3E4ABB2AC58` through `gpg-agent` on a workstation. Prime the agent before the batch build. For agentless continuous integration, provide the passphrase through the `MAVEN_GPG_PASSPHRASE` environment variable from a secret store.

Do not pass `gpg.passphrase` on the command line and do not copy a passphrase from `settings.xml` into shell history. The release profile enables Maven GPG Plugin best-practice enforcement.

== Candidate bundle

After the release-preparation pull request is merged, check out that exact commit and create a signed bundle without uploading it:

[source,shell]
----
mvn --batch-mode -Prelease \
  -Dgpg.keyname=E669C3E4ABB2AC58 \
  -DskipUpload=true \
  clean deploy
----

Run the command from the reactor root without a manual module list. Inspect `target/central-publishing/central-bundle.zip`. Confirm all publishable parent, core, JUnit, and server POMs and artifacts are present. Confirm main, source, Javadoc, signature, checksum, coordinate, license, dependency-scope, reproducibility, and SCM metadata.

== Maven Central

After explicit maintainer approval, upload the same verified commit:

[source,shell]
----
mvn --batch-mode -Prelease \
  -Dgpg.keyname=E669C3E4ABB2AC58 \
  clean deploy
----

The command uploads the signed bundle and waits for Central validation. It does not publish automatically. Open the Central Portal deployments page, inspect the validated deployment, and explicitly publish it. Record the deployment ID.

== Tag and GitHub release

After Central reports `PUBLISHED`:

[source,shell]
----
git tag -s <version> -m "FixMock <version>"
git push origin <version>
----

Create the GitHub release from the tag and finalized changelog. Resolve the released POMs and all published JARs from Maven Central using a fresh local Maven repository.

== Next development iteration

Set the parent, reactor modules, and external consumer fixture to the next development SNAPSHOT in a separate pull request. Keep README installation examples on the latest published release until the next release.

Update the Spring Boot starter through a separate dependency pull request and run its compatibility workflow against the released artifacts.

== Failed releases

Stop on any validation or publication failure. Published Maven artifacts are immutable. Do not replace a published version; prepare and verify a corrected patch release.
